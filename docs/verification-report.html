C2 · Proto priority ordinals ≠ domain weights

internal/domain/job.go:27-30 (0,2,5,10) vs proto/v1/job.proto:21-27 (1,2,3,4)

The enum values are quoted correctly. The failure mechanism is not: the review says a naively-cast HIGH (3) and CRITICAL (4) would sort below default (2). But 3 > 2 and 4 > 2 — order is preserved, only spacing is compressed (10→4, 5→3).

-- naive cast (hypothetical, no handler exists yet)
LOW 1 instead of 0  → slightly hotter than intended
DEFAULT 2 = 2       → coincidental match (review is right here)
HIGH 3 instead of 5 · CRITICAL 4 instead of 10 → compressed, still above 2

Keep the recommended explicit protoToDomainPriority() mapper — the UNSPECIFIED(0) ≡ PriorityLow(0) collision and mixed-write drift are real — but “silent scheduling corruption / sorts below default” must be retracted. Also speculative: no handler exists to perform the naive cast.

Only j.Status = next; trigger fixes the row, not the in-memory object returned to callers. Proposed j.UpdatedAt = time.Now().UTC() is valid (time already imported).

No MaxOutboxRetries, no dead-letter/abandoned path. A poisoned row would be re-fetched every tick. Suggested cap + skip/abandon rule is the right fix.
